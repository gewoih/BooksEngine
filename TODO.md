# Этап 2. Каталог в PostgreSQL

## 1. Инфраструктура БД: PostgreSQL + pgvector в docker compose

**Проблема.** БД нет; этап 2 и выдача рекомендаций в API опираются на Postgres с pgvector.

**Что сделать.** `docker-compose.yml` с `pgvector/pgvector:pg17`, том для данных, порт и пароль
из `.env`. Проверить, что тома хватит: каталог + 95M оценок + 116M `shelf_events` с индексами —
оценка ~15–20 ГБ, на диске сейчас ~30 ГБ свободно. `shelf_events` (116M строк) по умолчанию
**не грузить**: в модели оценок они не участвуют, польза от них как от неявного сигнала
не доказана (проверяется на этапе 3). Загрузка — отдельной командой, когда понадобятся.

**Где.** `docker-compose.yml`, `.env.example`.

---

## 2. Схема БД в EF Core-миграциях

**Проблема.** Схемой должен владеть C#-проект: позже ASP.NET API сам пишет оценки и полки
пользователей приложения. Python только наполняет готовые таблицы.

**Что сделать.** `dotnet/BooksEngine.Db` (.NET 10, Npgsql + Pgvector.EntityFrameworkCore).
Таблицы с расчётом на несколько источников и своих пользователей:
`sources`; `works`, `editions`, `authors`, `work_authors`, `genres`, `work_genres`;
`external_ids(source, entity_type, external_id → internal id)` — Goodreads-id не становится
первичным ключом каталога; `dataset_users` (с `source`) отдельно от `app_users`;
`ratings` с сырым значением и шкалой (`value`, `scale_max`: 5 для Goodreads, 10 для приложения);
`shelves` / `shelf_items` (to-read, reading, read, dnf); `work_embeddings(model_version, vector)`.
Решить и зафиксировать: оценки датасета — в той же таблице, что и оценки приложения, или
отдельно (95M строк против единиц тысяч — разные профили нагрузки).

**Где.** `dotnet/BooksEngine.Db/`.

## 3. Загрузка каталога: `booksengine load-db`

**Что сделать.** `COPY` из `data/clean/*.parquet` в таблицы, созданные миграциями; маппинг
внешних id Goodreads во внутренние через `external_ids`. После загрузки — сверка числа строк
с `manifest.json`, падение при расхождении. Идемпотентность: повторная загрузка того же
`manifest` ничего не дублирует.

**Где.** `src/booksengine/db_load.py` (новый), `cli.py`.

# Этап 3. Базовая модель рекомендаций

## 4. Отложенная выборка и протокол оценки

**Проблема.** Дат в `goodreads_interactions.csv` нет — временной сплит невозможен.

**Что сделать.** Per-user holdout: выборка тестовых пользователей, у каждого скрыто 20%
оценок, фиксированный seed, сплит сохраняется в `data/` и переиспользуется всеми моделями.
Релевантно — оценка ≥ 4 (из 5); подтвердить порог распределением (4–5 — 70% оценок).
Отдельный срез по «тяжёлым» и «лёгким» пользователям (10–20 оценок против сотен).

**Где.** `src/booksengine/model/split.py`.

---

## 5. Метрики ранжирования

**Что сделать.** NDCG@10/20, Recall@K, MAP@K, coverage каталога; отдельная метрика
«доля скрытых низких оценок (≤ 2) в топе» — негативный сигнал должен **снижать** её.
Из кандидатов исключаются уже оценённые пользователем произведения.

**Где.** `src/booksengine/model/metrics.py`.

---

## 6. Baseline: популярность

**Что сделать.** Байесовское среднее (сглаживание к глобальной средней) × число оценок.
Нижняя планка: любая CF-модель, не обогнавшая популярность, не принимается.

---

## 7. Кандидаты CF

**Что сделать.** item-kNN (центрированные по пользователю оценки, знаковое сходство,
понижение веса активных пользователей), EASE^R (на top-N произведений — матрица N×N в памяти),
ALS (`implicit`, confidence-взвешенный). Для всех — fold-in нового пользователя без
переобучения, такой линейной алгеброй, которую потом повторит C#-API.

---

## 8. Негативный сигнал: низкие оценки

**Проблема.** 1–2 балла — всего 8% оценок; модели на неявном сигнале трактуют любую оценку
как «понравилось».

**Что сделать.** Сравнить «центрирование по пользователю (низкая оценка — отрицательный вклад)»
с «игнорировать оценку» по метрике из п. 5 (доля плохих в топе) и по NDCG.

---

## 9. Разнонаправленный вкус

**Что сделать.** Кластеризация понравившихся пользователю произведений в пространстве
item-векторов → кандидаты из каждого кластера, чередование. Мерить точность и intra-list
diversity против одного вектора пользователя.

---

## 10. Чувствительность к порогу k-core (10, 20) против (10, 10)

**Проблема.** Порог 20 оценок у произведения выбран по доле оценок и размеру каталога модели,
не по качеству рекомендаций. Обещано проверить метрикой.

**Что сделать.** На одних и тех же тестовых пользователях: какая доля их скрытых книг вообще
попадает в модель и NDCG при k_work = 10 и 20. Если 10 заметно лучше — менять
`config/cleaning.yaml`.

---

## 11. Демо: оценки из CSV → рекомендации с объяснением

**Что сделать.** `booksengine recommend --ratings my.csv` (title / isbn / goodreads_id, rating
1–10). Сопоставление с каталогом: ISBN → точно; иначе нечётко по названию + автору (с учётом
`original_title` и названий всех изданий); несопоставленные — показать списком. Шкала 1–10 →
1–5. Объяснение: «потому что вы высоко оценили X, Y» (вклады соседей) + общие жанры/авторы.
Сборники (`is_collection`) не рекомендовать, если оценены их части.

**Где.** `tests/`.

## 17. Дубли произведений: одна книга под несколькими `work_id`

**Проблема.** Goodreads иногда заводит «теневое» произведение для той же книги. Модель считает
его отдельной позицией и может порекомендовать «The Hobbit» тому, кто уже оценил «The Hobbit».
Такой дефект заметен в выдаче сразу, в отличие от статистического шума.

**Чем подтверждается.** 2026-09-23, CF-ядро, группировка по нормализованному названию (без
скобок с серией и пунктуации) + первому автору: 1 599 групп, 8 726 произведений, 2.68M оценок.
Настоящие дубли есть: «The Hobbit» ×3 (152 405 / 26 / 23 оценки), «A Game of Thrones»
(113 142 / 20), «The Secret Garden» (57 136 / 37), «The Count of Monte Cristo» (46 499 / 38).
Но в эвристике много ложных совпадений: графические романы-адаптации («City of Bones:
Graphic Novel»), книги, разбитые на части («Order of the Phoenix, Part 1»), сборники,
а арабские названия после нормализации схлопываются в пустую строку (группы по 254 и 82
произведения). **Реальный масштаб не измерен**: 2.68M — верхняя граница, основная часть
приходится на главные произведения групп, не на дубли.

**Что сделать.** Сначала замерить честно: нормализация, которая сохраняет не-латинские буквы,
исключение адаптаций/частей/сборников, просмотр топа групп глазами. Дальше два варианта,
выбрать по данным: (а) слить теневые произведения в главное (оценки пересчитать в среднее,
как для изданий) — на этапе очистки; (б) только не выдавать в рекомендациях дубль того, что
пользователь уже оценил, — на этапе выдачи. Вариант (а) лучше для модели, если дублей
заметно; вариант (б) безопаснее, если эвристика шумная.

**Где.** `src/booksengine/data/clean.py` (правило + журнал), `config/cleaning.yaml`.
