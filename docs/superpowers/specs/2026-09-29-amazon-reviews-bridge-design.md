# Amazon Reviews'23: приём данных, мост на Goodreads, сигнал перевода

Первый шаг встраивания второго источника (пункт TODO «Книг после 2017 года модель не знает»). Дешёвая
проверка (2026-09-28) показала: мост по ISBN/ASIN — 16.5% книг Books, 22.9% Kindle; книг после 2017 с 100+
оценками — 4 907 (Books, Kindle не считали); профили пользователя/Леры нашлись на 92%/81%. Итог проверки —
толк есть.

Этот шаг не трогает модель, выдачу и БД — он готовит данные и отвечает на следующий открытый вопрос:
**у какой доли книг после 2017 вообще есть русский перевод** (без этого сигнала пункт «новые книги» не
советуется — решение принято раньше: терять хорошую непереведённую книгу лучше, чем предлагать её читающему
по-русски). Модель, новые произведения в каталоге, `source_id` у связей — следующий шаг, отдельным циклом,
после того как здесь станет видно, сколько книг реально проходят фильтр перевода.

## Сырьё

`RAW_DIR` (как Goodreads/MovieLens), 4 файла — 0-core `rating_only` и `raw/meta_categories`, категории
Books и Kindle_Store:

| файл | что | где взять |
|---|---|---|
| `Books.csv.gz`, `Kindle_Store.csv.gz` | `user_id, parent_asin, rating, timestamp`, без текста | `amazon-reviews-2023.github.io` → 0-Core → rating_only |
| `meta_Books.jsonl.gz`, `meta_Kindle_Store.jsonl.gz` | автор, ISBN-10/13, издатель+дата (текстом), язык, категории | `raw/meta_categories` на том же сайте |

Сервер McAuley Lab (`mcauleylab.ucsd.edu`) медленный (~0.8 МБ/с) и рвёт соединение на многогигабайтных файлах
(проверено при спайке — `meta_Books.jsonl.gz`, 4.9 ГБ, дважды обрывался на прямом `curl`). Устойчивое
скачивание — не часть `prepare` (в отличие от Goodreads/MovieLens файлы нельзя просто «положить в RAW_DIR
один раз руками» без борьбы с обрывами). Добавляю `scripts/fetch_amazon_raw.sh` — то же самое, что
`robust_download.sh` из спайка (докачка `-C -`, обрыв при зависании `--speed-limit`/`--speed-time`, повтор до
`Content-Length`), но в репозитории, разовый помощник, не в CLI `booksengine`.

## Модуль `src/booksengine/data/amazon.py`

Тот же DuckDB-паттерн, что `stage.py` — разбор форматов без фильтрации, оценки участвуют в статистике
битых строк.

**Рейтинги** (`stage_ratings`): `read_csv` обоих `rating_only` файлов, `source` — `'books'`/`'kindle'`
литералом колонки. Схема на выходе (`data/amazon/staging/ratings.parquet`): `user_id, parent_asin, rating,
timestamp, source`.

**Метаданные** (`stage_meta`): `read_json(format='newline_delimited', ignore_errors=true)` обоих
`meta_*.jsonl.gz` — так же, как `stage_editions` читает `goodreads_books.json`. Нужные поля: `parent_asin,
title, author.name, details['ISBN 10'], details['ISBN 13'], details['Publisher'] (текст с датой), details
['Language'], categories`. Год издания — регэксом из `Publisher` (в проверке нашлись единичные мусорные года
2085–2099 из шума в тексте — не критично для агрегатов, но при округлении «год издания» использовать
`min(4-значные числа в разумном диапазоне 1900–2026)`, не `max`, как было в спайке: `max` иногда цепляет левое
число из строки, `min` обычно — само издание).

**Мост** (`build_bridge`): читает `data/clean/editions.parquet` (`isbn`, `isbn13`, `asin`, `kindle_asin`,
`work_id`) книжного пайплайна (уже готов, не пересчитывается). Совпадение по `isbn10`/`isbn13` (только цифры
и `X`, без дефисов) — для Books; по `kindle_asin == parent_asin` — для Kindle (метаданные для этого не
нужны — сопоставление прямо по ID, как в спайке). Результат — `data/amazon/clean/bridge.parquet`:
`parent_asin, work_id` (`work_id IS NULL` — книги, которых в Goodreads нет).

**Экспорт** (`data/amazon/clean/`): `ratings.parquet` (после k-core — ниже), `items.parquet` (parent_asin,
title, author, isbn10, isbn13, year, categories, n_ratings, source), `bridge.parquet`.

## Очистка

Лёгкая — этот шаг не готовит вход для EASE (это фаза 3), только считает статистику и мост:

- k-core `clean.apply_kcore(min_user=5, min_work=5)` — переиспользуем как есть (внутри жёстко `user_id`/
  `work_id`, поэтому `parent_asin` временно переименовывается в `work_id` для вызова). Пороги ниже книжных
  (20/100): у Amazon оценки на человека редкие (в проверке только 134K/1.6M книжных пользователей — с 20+
  оценками; медиана — единицы), k-core 20/100 вымыл бы почти всё. 5/5 — тот же смысл (минимум статистики,
  не толпа из одного случайного человека), подобранный под плотность Amazon, не под Goodreads.
- `clean.filter_users` (low-variance, monotone, hyperactive) — не переиспользуем на этом шаге: пороги
  калибровались под Goodreads-профиль поведения, и здесь они не нужны — очистка входа для обучения будет
  сделана заново в фазе 3, когда решится, как две шкалы сочетаются.

## Сигнал перевода (Wikidata)

Только для новых книг (год издания после 2017) без моста (`bridge.work_id IS NULL`) и после k-core: отчёт
считает только их, а проверка всех книг без моста — тысячи пачек, часы запросов. Публичный SPARQL-эндпоинт
(`query.wikidata.org/sparql`) не рассчитан на тысячи одиночных запросов — пачками по ISBN-13 (`VALUES` до ~200
значений за запрос).

P212 в Wikidata хранится с дефисами по диапазонам регистрации (`978-1-944757-03-8`) — ни запись Amazon
(`978-1944757038`), ни голые цифры с ним не совпадают (проверено живым запросом; в первой версии дизайна
запрос шёл цифрами — перевод не нашёлся бы почти ни у одной книги). ISBN приводится к 13 цифрам с проверкой
контрольной цифры (ISBN-10 — переводится в 13), в запрос идут каноническая расстановка дефисов (`isbnlib.mask`)
и цифры:

```sparql
SELECT ?isbnraw ?hasRu WHERE {
  VALUES ?isbnraw { "978-1-944757-03-8" "9781944757038" ... }
  ?edition wdt:P212 ?isbnraw; wdt:P629 ?work .
  OPTIONAL { ?ruEdition wdt:P629 ?work; wdt:P407 wd:Q7737 . }
  BIND(BOUND(?ruEdition) AS ?hasRu)
}
```

Один ISBN бывает у нескольких элементов — перевод есть, если он есть хоть у одного. Результат — колонки в
`items.parquet`: `isbn13_n`, `wikidata` (`ru` / `found` — в Wikidata есть, русского нет / `absent` — в Wikidata
нет / пусто — не проверялась) и `ru_translation_known` (= `ru`; без сигнала — false, согласно решённому: не
советовать без сигнала). Кэш ответов — `data/amazon/wikidata_cache.parquet` (`isbn13, status, checked_at`),
пишется после каждой пачки; упавшая после повторов пачка не кэшируется как «нет перевода» — повторный прогон
её дозапросит.

## Прогон и отчёт

`uv run booksengine amazon-bridge` (новая команда, не часть `prepare` — второй источник, отдельный
жизненный цикл): staging → мост → k-core → Wikidata → `reports/amazon_bridge.md`. Отчёт — то же, что уже
посчитано в спайке (люди/книги/оценки по источникам, сила моста, книги после 2017 с достаточными оценками),
плюс новое: **из книг после 2017 без моста — сколько прошли `ru_translation_known`** (это число определяет
объём фазы «новые произведения»).

## Тесты

Юнит-тесты на `amazon.py` — на маленьком синтетическом `rating_only`/`meta` CSV/JSONL в `tmp_path`:
разбор колонок, извлечение года (в т.ч. кейс с шумовым 4-значным числом в тексте), сопоставление моста по
ISBN/ASIN на нескольких примерах (совпадение, несовпадение, отсутствие ISBN). Wikidata-запрос — тест на
моке HTTP-ответа (без реального похода в сеть в pytest), плюс отдельная ручная проверка на реальных данных
(как книжный `prepare` — pytest не гоняет полные прогоны).

## Что не входит в этот шаг

Модель (своя шкала весов Amazon, `source_id` у связей, смешивание с EASE-like), новые произведения в
каталоге (`works`/`authors`/`editions` для книг без Goodreads-карточки — нужны `худ/нон-фикшн` из Amazon
`categories`, проверка на дубли через `filters.Books.same`), отложенные Amazon-люди для замера, выдача —
следующий цикл, после того как здесь будет видно реальное число книг с переводом.
